# Project Audit Guide

This is a working checklist for a human review of the complete Halcyon / `alcyone` repository. It is an audit aid, not a statement that each item has already passed review. Record findings in the table near the end; do not treat a green build as a substitute for reading the source and understanding its effect on the installed system.

## How to use this guide

1. Start from the current checkout and note the commit, branch, and any local changes. Use `git ls-files` as the authoritative tracked-file inventory; keep the manual register limited to files present in the checkout.
2. Read the project constraints and build-order notes first. Then review the relevant file groups and trace each dependency in the cross-file map.
3. For every file, identify its purpose, inputs, outputs, privilege, runtime/build timing, and consumers. If it is data or an asset, inspect the actual contents rather than relying on its filename.
4. Compare claims in README, TODO, plans, and comments with the implementation. Treat plans and upstream-derived notes as historical context until confirmed in the current code.
5. Write findings with a concrete path and evidence, plus a practical impact and proposed disposition. Mark a checklist item complete only after examining the file and following material references.

## Current project boundary

- One published image: `ghcr.io/halcyon-linux/alcyone:stable` (Halcyon, Containerfile variant; the BlueBuild variant `ceyx` lives on the `bluebuild` branch).
- Fedora Atomic / bootc image based on `ghcr.io/ublue-os/base-main:44`; no desktop environment is installed. Hyprland is a future plan, not current behavior.
- Kernel and NVIDIA kmods are consumed from prebuilt `akmods`, `akmods-extra`, and `akmods-nvidia-open` images. The selected OGC kernel is pinned in the build inputs. Only `nct6687d` is included from the extra device kmods for the MSI Z790-P target.
- The source is primarily a Containerfile, shell scripts, systemd units, configuration, recipes, and static assets. There is no application-level unit-test suite. Build-time assertions in `build_files/finalization/verify` and the final bootc lint gate are the image checks.
- The `main` branch is a release branch: pushes trigger a build and publish. Review workflow, credential, signing, and cleanup changes as production-impacting changes.

## Audit dimensions

For each applicable file, ask:

| Dimension                        | Questions                                                                                                                                                                                                        |
| -------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Purpose and ownership            | Is the file still used? Is its owner the image, an installed RPM, an upstream import, or a future plan? Is there a single authoritative copy?                                                                    |
| Reachability                     | What copies, imports, sources, enables, downloads, invokes, or verifies it? Can its removal leave a dangling reference? Can it be overwritten by a package or later overlay?                                     |
| Safety                           | Does it run as root, at boot, at login, or in CI? Are arguments, paths, URLs, secrets, permissions, and failure modes handled safely? Could it mutate host state or unexpectedly reboot/change kernel arguments? |
| Reproducibility and supply chain | Are versions, digests, repositories, action SHAs, release assets, and upstream URLs sufficiently pinned and validated? Are downloaded artifacts attributed and tagged?                                           |
| Immutable-image fit              | Does persistent static content live under `/usr`? Is `/etc` only a default/override? Is `/var` content recreated at runtime if finalization strips it? Will bootc lint accept the result?                        |
| Runtime behavior                 | Do systemd ordering, conditions, enablement, user/system scope, and `WantedBy` match the intended behavior? Are required binaries/packages installed before units are enabled?                                   |
| Verification and documentation   | Does `verify` express the intended positive and negative invariants? Do docs, file maps, workflow triggers, and project guidance agree with the current tree?                                                    |

## Order-sensitive build path

Read `Containerfile` top to bottom and check the actual call graph. The intended order is:

1. Resolve Fedora/base/kernel inputs and build-only stages (`akmods`, `akmods-extra`, `akmods-nvidia`, `brew`, and the scratch `ctx` stage).
2. Copy desktop defaults and Homebrew payload, then install the pinned kernel and the selected extra kmod.
3. Enable/configure the baseline repositories, then run `install-cli-tools` followed by `install-utils`. Each script enables its own Halcyon COPR, sets priority 1, installs its complete package registry without `--from-repo`, and disables that COPR before returning. Continue with the patched gaming stack, common packages, Steam/Lutris, picker, and media automount.
4. Copy `system_files/overrides/` after package installation so intentional overrides win. Configure desktop integration, compose the base justfile, enable services, and add integration files. System repository policy runs after the NVIDIA package transaction, so build-only repositories are disabled after package installation is complete.
5. Copy NVIDIA payload, remove conflicting firmware, install matching NVIDIA packages, then enable NVIDIA services and apply NVIDIA finalization.
6. Re-run `image-info`, initramfs generation, and finalization so the final initramfs and metadata include NVIDIA; run `verify final`, then `bootc container lint` last.

For every package-installing `RUN`, check that `/ctx/shared/cleanup` still runs at the end. Check that every script path resolves from the `/ctx` bind mount, every downloaded GitHub artifact uses `/ctx/shared/ghcurl`, and each relevant `RUN` mounts `GITHUB_TOKEN`. Confirm no intermediate cleanup removes files needed by a later stage.

## Manual file register

Use the boxes as a personal progress tracker. The short prompts are starting points; inspect the complete file and its callers. `git ls-files` is the source for the current tracked-path inventory, including assets. Binary images should be opened and visually inspected; YAML/JSON/TOML/Just/shell should be read as executable or active configuration, not treated as inert documentation.

### Image build scripts (`build_files/`)

#### Finalization and validation

- [x] `build_files/finalization/finalize` — **Necessary bootc cleanup/account migration.** It prunes transient `/var` directories while preserving cache, recreates world-writable sticky `/var/tmp`, removes visible `/tmp` contents while `/tmp` is a tmpfs mount, relocates non-root passwd/group rows to `/usr/lib`, and resets `/etc` to root/wheel. The tmpfs prevents cleanup from traversing the read-only RPM bind mounts used in earlier Containerfile steps. Account keep patterns are anchored to exact usernames. The persistence check fails the build if relocated entries are missing. Source: [bootc user/group guidance](https://bootc.dev/bootc/building/bootc-users-and-groups).
- [x] `build_files/finalization/image-info` — **Needed for image identity and OS branding.** JSON metadata is serialized with `jq`, avoiding malformed JSON when input values contain quotes or newlines. Local builds now pass the logical image name and current branch; the stable image tag and GHCR ref remain the canonical published update target. The `IMAGE_VENDOR` default matches `halcyon-linux`.
- [x] `build_files/finalization/verify` — **Stage assertions cover baseline repository presence, all 57 Halcyon COPR packages, core image packages, NVIDIA artifacts, image metadata, initramfs, and obsolete paths.** Final verification also fails if either Halcyon COPR remains enabled. Fedora 44 QEMU driver dependencies provide the transitive `swtpm-tools` requirement. Sources: [Fedora 44 QEMU driver dependencies](https://packages.fedoraproject.org/pkgs/libvirt/libvirt-daemon-driver-qemu/fedora-44.html), [CLI package installer](build_files/packages/install-cli-tools), [utility package installer](build_files/packages/install-utils).

#### Kernel

- [x] `build_files/kernel/build-initramfs` — **Correct and needed for the pinned installed kernel.** It queries the installed kernel package, creates a no-hostonly reproducible zstd initramfs with OSTree/FIDO2 support under that kernel’s module directory, and applies mode `0600`. It runs after image metadata in both pre- and post-NVIDIA phases; `verify` later requires the final file.
- [x] `build_files/kernel/install-kernel-akmods` — **Correct for installing the matching prebuilt kernel and only the selected board kmod; required for the image.** It temporarily bypasses rpm-ostree/dracut kernel hooks, removes inherited kernel packages/modules, installs the mounted kernel RPMs, versionlocks them, installs only `nct6687d` from extra artifacts, then restores hooks. A failed RUN cannot publish a partially modified layer. The comment path in `Containerfile` is stale; no other file should be restored from extra kmods without changing the device-specific verification policy.
- [x] `build_files/kernel/install-kmods` — **Correct helper with deliberate no-match tolerance because the caller verifies required packages afterward.** It expands the supplied RPM globs and skips unmatched paths instead of aborting; `verify kernel` then requires both `kmod-nct6687d` and `nct6687d`, so a missing required payload fails the build. Needed by the kernel installer; do not use it for required kmods without a corresponding assertion.

#### NVIDIA

- [x] `build_files/nvidia/configure-nvidia` — **Correct conditional removal of the conflicting Nouveau firmware package; optional at build time, but required when the base includes it.** It checks RPM presence before removal and fails the RUN if DNF cannot remove it, which prevents continuing with the conflicting firmware payload. Needed only for the NVIDIA variant’s driver coexistence policy.
- [x] `build_files/nvidia/finalize-nvidia` — **Necessary NVIDIA post-install configuration.** The justfile import is idempotent, the NVIDIA `nvidia_peermem` config entry is removed before the regenerated initramfs, Firefox defaults are copied without replacing the distinct file names, powerd and Flatpak sync units are enabled, persistence and Waydroid are disabled, and modeset config is copied into immutable `/usr/lib`. The unreliable system-level Flatpak notification unit is no longer enabled; users can run the corrected manual status/retry recipe.
- [x] `build_files/nvidia/install-nvidia-driver` — **Correctly installs matching prebuilt NVIDIA artifacts and 32/64-bit EGL bridges; required for this image.** It temporarily enables Terra Mesa and the staging COPR, invokes the mounted `nvidia-install.sh` with the upstream `IMAGE_NAME=SKIP_PACKAGE_INSTALL`, `AKMODNV_PATH`, and `MULTILIB=1` contract, creates the NVML compatibility symlink, then disables the build-only repos. If any install step fails, the container RUN fails and the incomplete layer is not published; successful runs restore the intended repo state. Sources: [upstream Bazzite installer invocation](https://github.com/ublue-os/bazzite/blob/main/Containerfile), [local NVIDIA verifier](build_files/finalization/verify).

### Severity guide

- **Critical** — likely credential/private key exposure, unauthorized publish/signing, or a boot/update failure affecting all users.

- **Medium** — material feature failure, unsafe policy, surprising state mutation, or unverified supply-chain dependency with a plausible impact.
- **Low** — bounded defect, stale documentation, maintainability issue, or behavior affecting a narrow optional path.
- **Note** — intentional tradeoff, confirmed absence, or question resolved with evidence; keep it out of the defect count.
