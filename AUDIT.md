# Project Audit Guide

This is a working checklist for a human review of the complete Halcyon / `alcyone` repository. It is an audit aid, not a statement that each item has already passed review. Record findings in the table near the end; do not treat a green build as a substitute for reading the source and understanding its effect on the installed system.

## How to use this guide

1. Start from the current checkout and note the commit, branch, and any local changes. This checkout has no `tree.list`; use `git ls-files` as the authoritative tracked-file inventory and treat any absent paths below as stale register entries.
2. Read the project constraints and build-order notes first. Then review the relevant file groups and trace each dependency in the cross-file map.
3. For every file, identify its purpose, inputs, outputs, privilege, runtime/build timing, and consumers. If it is data or an asset, inspect the actual contents rather than relying on its filename.
4. Compare claims in README, TODO, plans, and comments with the implementation. Treat plans and upstream-derived notes as historical context until confirmed in the current code.
5. Write findings with a concrete path and evidence, plus a practical impact and proposed disposition. Mark a checklist item complete only after examining the file and following material references.

## Current project boundary

- One published image: `ghcr.io/halcyon-linux/alcyone:stable` (Halcyon, Containerfile variant; the BlueBuild variant `ceyx` lives on the `bluebuild` branch).
- Fedora Atomic / bootc image based on `ghcr.io/ublue-os/base-main:44`; no desktop environment is installed. Hyprland is a future plan, not current behavior.
- Kernel and NVIDIA kmods are consumed from prebuilt `akmods`, `akmods-extra`, and `akmods-nvidia-open` images. The selected OGC kernel is pinned in the build inputs. Only `nct6687d` is included from the extra device kmods for the MSI Z790-P target.
- The source is primarily a Containerfile, shell scripts, systemd units, configuration, recipes, and static assets. There is no application-level unit-test suite. Build-time assertions in `build_files/finalization/verify` and the final bootc lint gate are the image checks.
- The `main` branch is a release branch: pushes trigger a build and publish. Review workflow, credential, signing, and cleanup changes as production-impacting changes.

## Audit dimensions

For each applicable file, ask:

| Dimension                        | Questions                                                                                                                                                                                                        |
| -------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Purpose and ownership            | Is the file still used? Is its owner the image, an installed RPM, an upstream import, or a future plan? Is there a single authoritative copy?                                                                    |
| Reachability                     | What copies, imports, sources, enables, downloads, invokes, or verifies it? Can its removal leave a dangling reference? Can it be overwritten by a package or later overlay?                                     |
| Safety                           | Does it run as root, at boot, at login, or in CI? Are arguments, paths, URLs, secrets, permissions, and failure modes handled safely? Could it mutate host state or unexpectedly reboot/change kernel arguments? |
| Reproducibility and supply chain | Are versions, digests, repositories, action SHAs, release assets, and upstream URLs sufficiently pinned and validated? Are downloaded artifacts attributed and tagged?                                           |
| Immutable-image fit              | Does persistent static content live under `/usr`? Is `/etc` only a default/override? Is `/var` content recreated at runtime if finalization strips it? Will bootc lint accept the result?                        |
| Runtime behavior                 | Do systemd ordering, conditions, enablement, user/system scope, and `WantedBy` match the intended behavior? Are required binaries/packages installed before units are enabled?                                   |
| Verification and documentation   | Does `verify` express the intended positive and negative invariants? Do docs, file maps, workflow triggers, and project guidance agree with the current tree?                                                    |

## Order-sensitive build path

Read `Containerfile` top to bottom and check the actual call graph. The intended order is:

1. Resolve Fedora/base/kernel inputs and build-only stages (`akmods`, `akmods-extra`, `akmods-nvidia`, `brew`, and the scratch `ctx` stage).
2. Copy desktop defaults and Homebrew payload, then install the pinned kernel and the selected extra kmod.
3. Enable/configure repositories, install the patched gaming stack, remove superseded packages, install common packages, Steam/Lutris, picker, and media automount.
4. Copy `system_files/overrides/` after package installation so intentional overrides win. Configure desktop integration, compose the base justfile, set package/repository policy, enable services, add integration files, then run the first `image-info`, initramfs build, and finalization pass.
5. Copy NVIDIA payload, remove conflicting firmware, install matching NVIDIA packages, then enable NVIDIA services and apply NVIDIA finalization.
6. Re-run `image-info`, initramfs generation, and finalization so the final initramfs and metadata include NVIDIA; run `verify final`, then `bootc container lint` last.

For every package-installing `RUN`, check that `/ctx/shared/cleanup` still runs at the end. Check that every script path resolves from the `/ctx` bind mount, every downloaded GitHub artifact uses `/ctx/shared/ghcurl`, and each relevant `RUN` mounts `GITHUB_TOKEN`. Confirm no intermediate cleanup removes files needed by a later stage.

### Image build scripts (`build_files/`)

#### Finalization and validation

- [x] `build_files/finalization/finalize` — **Necessary bootc cleanup/account migration with a username-matching weakness.** It prunes transient `/var` directories while preserving cache, recreates world-writable sticky `/var/tmp`, removes `/tmp` content, relocates non-root passwd/group rows to `/usr/lib`, and resets `/etc` to root/wheel. The persistence check is useful, but its keep regexes (`root`, `root|wheel`) are unanchored and match anywhere in an entire account row; anchor usernames/fields so unusual account names or paths cannot be retained accidentally. It is required to produce the intended immutable account layout. Source: [bootc user/group guidance](https://bootc.dev/bootc/building/bootc-users-and-groups).
- [x] `build_files/finalization/image-info` — **Needed for image identity/OS branding and correctly runs before each initramfs generation, but assumes trusted values.** It writes the JSON consumed by the verifier and modifies `/usr/lib/os-release`; values come from controlled CI arguments in the published path. Direct heredoc interpolation is not JSON-escaped, and `image-tag` is hardcoded to `stable`; arbitrary quote/newline build args or a testing/unstable branch could make metadata invalid or misleading. Local build also inherits `IMAGE_VENDOR=ublue-os`. Keep, but encode JSON with a serializer and align tag/vendor with the actual output reference.
- [x] `build_files/finalization/verify` — **Strong and necessary stage guard set; package assertions are internally supported by Fedora dependencies.** It checks kernel/kmods, repos, required/forbidden RPMs, image metadata/ref, initramfs, downloaded executables, justfile parsing, libvirtd, renamed helper binaries/units/enabled links, and selected stale paths. Fedora 44’s QEMU driver has a hard dependency on `swtpm-tools`, so the verifier’s virtualization requirement is pulled in by the installed libvirt stack even though it is not listed directly in `common_packages`. The helper-unit gate is stronger than the general service enable script but does not assert every optional service. Sources: [Fedora 44 QEMU driver dependencies](https://packages.fedoraproject.org/pkgs/libvirt/libvirt-daemon-driver-qemu/fedora-44.html), [local package set](build_files/packages/install-common-packages).

It runs after image metadata in both pre- and post-NVIDIA phases; `verify` later requires the final file.
- [x] `build_files/kernel/install-kernel-akmods` — **Correct for installing the matching prebuilt kernel and only the selected board kmod; required for the image.** It temporarily bypasses rpm-ostree/dracut kernel hooks, removes inherited kernel packages/modules, installs the mounted kernel RPMs, versionlocks them, installs only `nct6687d` from extra artifacts, then restores hooks. A failed RUN cannot publish a partially modified layer. The comment path in `Containerfile` is stale; no other file should be restored from extra kmods without changing the device-specific verification policy.
- [x] `build_files/kernel/install-kmods` — **Correct helper with deliberate no-match tolerance because the caller verifies required packages afterward.** It expands the supplied RPM globs and skips unmatched paths instead of aborting; `verify kernel` then requires both `kmod-nct6687d` and `nct6687d`, so a missing required payload fails the build. Needed by the kernel installer; do not use it for required kmods without a corresponding assertion.

#### Shared and system configuration

- [x] `build_files/shared/cleanup` — **Correct build-layer cleanup and needed after package-install steps.** It removes visible `/tmp` contents, the DNF5 log and visible/hidden `/boot` entries; callers that need `/tmp` artifacts use tmpfs mounts or consume them before cleanup. The `|| true` guards can hide cleanup errors, and `/tmp/.*` is not explicitly removed, but build callers use fresh temporary mounts and finalization performs another cleanup.
- [x] `build_files/shared/dnf5-setopt` — **Incorrect helper; its only caller silently suppresses the resulting failure, so it is not currently applying the intended option.** `${1##.}` removes one arbitrary leading character (`enabled=0` becomes `nabled=0`), and the `_v` default assignment is only evaluated once, so multiple options repeat the first value. `die()` exits with status 0, masking invalid inputs. The caller wraps its `eval` with `|| true`, so the wildcard `negativo17` enable-disable request is ineffective. Either repair this helper and check the call or remove the unused abstraction. Source: [DNF5 config-manager setopt documentation](https://github.com/rpm-software-management/dnf5/blob/main/doc/dnf5_plugins/config-manager.8.rst).

These are optional scheduler preferences, not required for device operation. Sources: [systemd-udev `ATTR` and pattern matching](https://www.freedesktop.org/software/systemd/man/262/udev.html), [kernel scheduler switching interface](https://docs.kernel.org/block/switching-sched.html), [BFQ behavior](https://docs.kernel.org/block/bfq-iosched.html).

RTD3 also depends on compatible hardware/ACPI and runtime power management for the relevant PCI functions; a GPU driving a display may remain active. Keep this for the image’s optional power-saving policy, especially hybrid laptops, but do not treat the options as effective or beneficial on every NVIDIA machine. Sources: [NVIDIA RTD3 documentation](https://download.nvidia.com/XFree86/Linux-x86_64/615.71.09/README/dynamicpowermanagement.html), [NVIDIA S0ix documentation](https://download.nvidia.com/XFree86/Linux-x86_64/615.71.09/README/powermanagement.html), [local NVIDIA image build](Containerfile).
- [x] `system_files/nvidia/usr/lib/systemd/system/nvidia-flatpak-runtime-sync.service` — **Correct and needed for the NVIDIA image’s automatic Flatpak driver-runtime sync; not needed for core NVIDIA display or non-Flatpak use.** The executable path is part of the locally installed `nvidia-flatpak-runtime` package contract and is checked by the local verifier; the NVIDIA finalizer enables this unit. Its NVIDIA-module and OSTree conditions keep it off non-NVIDIA/live environments. The `check` convention is correct: the matching upstream helper exits 0 when runtimes need syncing (so `ExecStart` runs) and 1 when already synced (so systemd skips it); systemd documents exit codes 1–254 from `ExecCondition` as a non-failure skip. `network-online.target`, a 600-second start timeout, and failure retries support boot-time Flatpak installation, though an unavailable network/remote can cause repeated retries every 30 seconds. Keep for automatic matching of system driver and Flatpak GL extensions. Sources: [local package list](build_files/packages/install-common-packages), [local NVIDIA finalizer](build_files/nvidia/finalize-nvidia), [local verifier](build_files/finalization/verify), [upstream helper check/sync behavior](https://raw.githubusercontent.com/ublue-os/bazzite/main/system_files/nvidia/shared/usr/libexec/ublue-nvidia-flatpak-runtime-sync), [systemd `ExecCondition` semantics](https://www.freedesktop.org/software/systemd/man/257/systemd.service.html).
- [x] `system_files/nvidia/usr/lib/systemd/system/nvidia-flatpak-runtime-verify.service` — **The conditions and “notify only if still mismatched” check are sensible, but the unit is not reliably wired to run or notify.** The local NVIDIA finalizer enables it and its module/OSTree checks are appropriate. However, `WantedBy=graphical.target` creates a target-to-service `Wants` dependency, and systemd orders a target after units it wants; this unit also says `After=graphical.target`, forming an ordering cycle that systemd must break. Remove that reverse ordering or trigger it from a suitable user-session target. Separately, this is a system service with no `User=`, session-bus address, or user-service handoff, while the upstream notifier it invokes uses `notify-send` and desktop commands. The Desktop Notifications protocol is session-bus scoped, and system services do not normally inherit the graphical user manager’s environment, so the notification is not dependable; a failure can be retried every 30 seconds. The helper source is supplied by an external package, not this repository, so its exact packaged implementation was not independently inspected. This service is optional notification UX; the sync unit handles the actual runtime installation. Sources: [local NVIDIA finalizer](build_files/nvidia/finalize-nvidia), [systemd target ordering defaults](https://www.freedesktop.org/software/systemd/man/260/systemd.target.html), [systemd `WantedBy` semantics](https://www.freedesktop.org/software/systemd/man/257/systemd.unit.html), [systemd service environment](https://www.freedesktop.org/software/systemd/man/260/systemd.exec.html), [Desktop Notifications session-bus requirement](https://specifications.freedesktop.org/notification/latest-single/), [upstream notifier implementation](https://raw.githubusercontent.com/ublue-os/bazzite/main/system_files/nvidia/shared/usr/libexec/ublue-nvidia-flatpak-runtime-notify), [systemd `ExecCondition` semantics](https://www.freedesktop.org/software/systemd/man/257/systemd.service.html).
- [x] `system_files/nvidia/usr/lib/udev/rules.d/80-nvidia-pm.rules` — **Partly correct power-management rules; the unconditional USB-controller removals are obsolete for this image’s kernel and can disable hardware.** The vendor/class matches for NVIDIA VGA/3D devices and the `power/control=auto` on add/bind with restoration to `on` at unbind are valid runtime-PM operations. But NVIDIA’s current driver documentation says removing the GPU’s USB xHCI and Type-C UCSI functions is no longer required on Linux 5.5 or later; this project currently pins a 7.2.7 kernel. Those first two rules can therefore needlessly remove the GPU’s USB/USB-C controller functions (including ports used for USB-C/VirtualLink), so remove them unless disabling those functions is a deliberate compatibility choice. The audio-removal rule is commented out. The active rules are useful for RTD3 power savings on supported hardware, not required for basic graphics; NVIDIA notes maximum savings depend on runtime PM being enabled for the PCI functions. Sources: [NVIDIA RTD3 rules and kernel-version guidance](https://download.nvidia.com/XFree86/Linux-x86_64/615.71.09/README/dynamicpowermanagement.html), [local kernel pin](Containerfile), [upstream NVIDIA udev rules](https://raw.githubusercontent.com/ublue-os/bazzite/main/system_files/nvidia/shared/usr/lib/udev/rules.d/80-nvidia-pm.rules).
- [x] `system_files/nvidia/usr/share/ublue-os/firefox-config/02-bazzite-nvidia.js` — **Valid Firefox preference-file syntax and correctly installed as a separate NVIDIA default, but it force-enables an optional graphics path.** `widget.dmabuf.force-enabled` is a real Firefox preference; it can override the graphics blocklist for DMA-BUF, but it cannot guarantee that the runtime/device combination supports the path and may expose rendering or video issues. The NVIDIA finalizer copies all `*.js` files in the configuration directory into RPM Firefox’s `defaults/pref`; the `02-` name is distinct from the global `01-` file, so this does not overwrite or merge-conflict with it. Flatpak Firefox does not read this RPM defaults directory. Keep only if forcing this Wayland/DMA-BUF behavior on the NVIDIA variant is intentional and supported by hardware testing; it is not required for Firefox or system operation. Sources: [Mozilla DMABUF/blocklist behavior](https://bugzilla.mozilla.org/show_bug.cgi?id=1788573), [local NVIDIA copy/enable logic](build_files/nvidia/finalize-nvidia), [global Firefox defaults](system_files/desktop/usr/share/ublue-os/firefox-config/01-bazzite-global.js).
- [x] `system_files/nvidia/usr/share/ublue-os/just/95-bazzite-nvidia.just` — **Useful only as an optional manual status/retry command, but incorrect in both status and error reporting.** `get_status_token` captures the helper output into `service_state`, then `if ! service_state;` tries to execute a command literally named `service_state` instead of testing the variable; the command is not found, so the function always prints `upgraded`, even when versions mismatch. In the `upgrade` branch, a failed `nvidia-flatpak-runtime-sync sync` is followed by unconditional `exit 0`, falsely reporting success. Invalid options also fall through to success. Add explicit status-code/output handling, propagate sync failure, and reject unknown options. There is no image/driver rollback operation here; it only invokes the Flatpak runtime installer, so the main need is a reliable manual retry after automatic sync failure. Keep only if that user-facing retry/status command is desired. Sources: [local recipe](system_files/nvidia/usr/share/ublue-os/just/95-bazzite-nvidia.just), [local importer](build_files/nvidia/finalize-nvidia), [local runtime helper package](build_files/packages/install-common-packages), [upstream helper exit/output behavior](https://raw.githubusercontent.com/ublue-os/bazzite/main/system_files/nvidia/shared/usr/libexec/ublue-nvidia-flatpak-runtime-sync).

## Repository-wide checks while reviewing

- Track executable mode as well as contents: build and local scripts, references, and Tuned scripts are expected to be executable; static configuration should not be.
- For every new or removed runtime package, trace its unit, recipe, policy, and `verify` assertions. For every new `.just` file, inspect the importer and any yafti references.
- For repositories, inspect both setup and shipping disable policy. Adding a repository/COPR, kernel module, changing the base image, removing versionlocks, or changing workflow signing/publishing/cleanup requires particular care under the project rules.
- For any external download, record the source and pinning, verify architecture/asset selection and checksum/signature strategy where available, and confirm the build secret is mounted only where required.
- Confirm static payload is not placed under `/var`; inspect whether all retained files are necessary and whether finalization removes their paths.
- Treat references to Waydroid, bundled fonts, offline docs, trimmed kmods and renamed helper units as deliberate guardrails. A finding that proposes reintroducing one must include the matching deliberate `verify` update and rationale.
- Remember the known tooling quirks: local build tags and the image-management filter now both use `alcyone*-build`; the helper only permits the `alcyone` image (or `containerfile`); docs changes may not trigger the build workflow because `.md`/`.txt` paths are ignored; a main push publishes the image.

### Severity guide

- **Critical** — likely credential/private key exposure, unauthorized publish/signing, or a boot/update failure affecting all users.
- **High** — likely privilege escalation, data loss, broken boot/runtime core path, or release-integrity failure.
- **Medium** — material feature failure, unsafe policy, surprising state mutation, or unverified supply-chain dependency with a plausible impact.
- **Low** — bounded defect, stale documentation, maintainability issue, or behavior affecting a narrow optional path.
- **Note** — intentional tradeoff, confirmed absence, or question resolved with evidence; keep it out of the defect count.
