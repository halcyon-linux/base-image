## 2. What that audit is doing

After installing everything, the applications script checks where each package put files outside the normal system directories. It runs the equivalent of:

```bash
rpm -ql "$pkg" | grep -E '^/(opt|var)'
```

and prints every path under `/opt` or `/var`.

This was meant to be an awareness check for applications that do not follow the usual `/usr` layout. It is not a verification gate; it does not install or enable anything. It just prints the paths.

The problem is that modern browsers and office suites ship thousands of files. In this run the audit produced:

| Package | Start line | Notes |
|---|---:|---|
| bitwarden | 7423 | first package with `/opt` files |
| ferdium | 7512 | packed web app |
| mullvad-vpn | 8126 | |
| onlyoffice-desktopeditors | 8211 | thousands of editor/theme assets |
| opencode-desktop | 12849 | |
| private-internet-access | 12945 | |
| ticktick | 13781 | |
| brave-browser | 13859 | |
| google-chrome-stable | 14104 | |
| microsoft-edge-stable | 14367 | line 14516 is inside this block |
| vivaldi-stable | 14746 | last package; audit ends at line 16162 |

That is **8,740 lines** from line 7423 to 16162. The Edge locale files alone are a wall of `.pak` files. Nothing is wrong with them; the audit is simply too literal.

The script now prints one line per package instead:

```text
INFO: Package microsoft-edge-stable ships 379 path(s) under /opt or /var: /opt/microsoft/msedge
```

The count and top-level directories preserve the useful information without the file-by-file dump.

## 3. What happens after the audit

### 3.1 The blank `Disabling repository:` lines — 30 minutes lost

Immediately after the Vivaldi paths, lines 16163–16168 contain six lines:

```text
Disabling repository:
Disabling repository:
Disabling repository:
Disabling repository:
Disabling repository:
Disabling repository:
```

Their timestamps are:

```text
05:42:39
05:47:39
05:52:39
05:57:39
06:02:40
06:07:40
```

One every five minutes. The applications verification then starts at **06:12:40**, another five minutes after the last line.

This was not a network hang. The cleanup trap iterated over `ENABLED_REPOS`, but the code used:

```bash
ENABLED_REPOS=("${ENABLED_REPOS[@]/code}")
```

That substitutes the matching element with an **empty string** instead of removing it. The trap therefore called:

```bash
dnf5 -y config-manager setopt ".enabled=0"
```

for each empty entry. That command is invalid, so the `dnf5` retry shim retried it six times with 60-second waits — about five minutes per empty entry. The errors were hidden by `2>/dev/null || true`, so the log showed only a blank `Disabling repository:` line, then silence.

**Six empty entries × five minutes = about 30 minutes of pure waiting.** That is the main reason this Build Image step took 48 minutes instead of roughly 18.

The cleanup now clears the array after each successful disable, because the repositories are installed strictly one at a time:

```bash
ENABLED_REPOS=()
```

It also prints the real name before each disable:

```text
Disabling repository: code
Disabling repository: gitlab.com_paulcarroty_vscodium_repo
Disabling repository: brave-browser
Disabling repository: google-chrome
Disabling repository: microsoft-edge
Disabling repository: vivaldi
```

If a later package fails, the trap still contains only the repository that is actually still enabled, so it prints and disables the right one.

## 4. The “Status Code 404”

There are two unrelated 404s in this context.

### 4.1 The 404 inside the build log: stale Fedora mirrors

At 06:14:55–56, during the NVIDIA driver transaction, dnf printed many lines like:

```text
>>> Status code: 404 for http://paducahix.mm.fcix.net/fedora/linux/updates/44/Everything/x86_64/Packages/x/xorg-x11-server-common-21.1.24-1.fc44.x86_64.rpm
>>> Status code: 404 for https://ziply.mm.fcix.net/.../xorg-x11-server-Xorg-21.1.24-1.fc44.x86_64.rpm
>>> Status code: 404 for https://mirror.cs.princeton.edu/.../xorg-x11-server-common-21.1.24-1.fc44.x86_64.rpm
```

Two packages were affected:

- `xorg-x11-server-common-21.1.24-1.fc44`
- `xorg-x11-server-Xorg-21.1.24-1.fc44`

Both are in the Fedora `updates` repository. A freshly published update was already in the repository metadata, but several mirrors had not received the RPM files yet. dnf’s mirrorlist therefore offered mirrors that returned 404.

This is a **mirror sync race, not a missing package or a broken repository**. The proof is in the same log:

```text
[15/16] xorg-x11-server-common-0:21.1.2 100% | ... | 36.0 KiB | 00m03s
[16/16] xorg-x11-server-Xorg-0:21.1.24- 100% | ... | 1.5 MiB | 00m03s
[16/16] Total 100% | 2.6 MiB/s | 12.9 MiB | 00m05s
Running transaction
```

Both packages reached 100% and the transaction continued. dnf fell back to a mirror that had synced. The 404 lines are noise from the failed mirror attempts, not fatal errors.

No action is needed for this. It will happen occasionally when Fedora publishes an update and the mirror network is still catching up.

### 4.2 The GitHub log API 404

While the job is still running, GitHub has not uploaded the job log archive. These endpoints return HTTP 404 / `BlobNotFound` for an in-progress job:

- `GET /repos/{owner}/{repo}/actions/jobs/{job_id}/logs`
- the per-step log endpoint

The web UI can show live logs through its authenticated streaming connection, but `gh run view --log`, `gh api`, and similar tools cannot retrieve live log text. The archive appears only after the whole job completes.

This is expected GitHub behavior. It is not a build error, and it is why the log download failed until the run finished.
